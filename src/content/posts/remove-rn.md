우리 앱은 React Native로 시작했다. 그 위에 네이티브 화면이 하나둘 얹히면서, React Native 껍데기 안에 Kotlin 화면이 들어앉은 구조가 됐다.

네이티브로 전환하자고 계획한 건 1년 반쯤 전이다. 그때부터 Compose 전환 브랜치를 만들어 조금씩 준비했다. 올해 들어 화면을 본격적으로 옮기기 시작했고, 10월에 React Native를 지우는 PR을 머지했다. 그동안 기능 개발은 멈추지 않았다.

이 글은 그 과정에서 지킨 규칙들을 적은 것이다.

## 왜 걷어내기로 했나

계획서 첫 줄에 적은 이유는 이것이다. React Native 버전을 올릴 때마다 네이티브 코드가 영향을 받는다.

섞여 있는 구조에서는 양쪽의 단점을 다 가진다. 대표적인 게 채팅 화면이었다. 채팅은 네이티브로 짰지만 React Native 화면 안에 끼워 넣어야 했다. 그러려면 Fragment여야 했고, 뷰를 끼우는 쪽에서는 매 프레임 레이아웃을 손으로 다시 맞추고 있었다. 키보드 높이는 전역 변수로 주고받았다. Fragment를 만드는 경로가 두 개였는데 둘 다 실패할 때 아무 소리도 내지 않았다.

이 화면에서 반복되던 크래시는 [다른 글](/posts/chat-crashes/)에 적었다. 원인을 거슬러 올라가면 "React Native 안에 끼워야 해서"였다.

빌드도 마찬가지였다. [CI를 붙이면서](/posts/android-ci/) 세어보니 빌드 태스크 1,078개 중 우리 코드에서 나오는 건 150개쯤이었다. 나머지는 대부분 React Native 라이브러리 모듈이었다.

## 규칙 1. 새 화면은 React Native에 만들지 않는다

가장 먼저 한 일은 옮기는 게 아니라 멈추는 것이었다. 새 화면은 React Native에 추가하지 않는다. 전부 네이티브로 만든다.

옮길 화면이 계속 늘어나면 마이그레이션은 끝나지 않는다. 한쪽에서 옮기는 동안 다른 쪽에서 새로 쌓이면 안 된다.

## 규칙 2. 한 번에 하지 않는다

빅뱅은 하지 않았다. 기능 개발과 병행했고, 계획상 비율은 기능 7에 마이그레이션 3이었다.

전부 멈추고 다시 쓰는 편이 깔끔해 보이지만, 그동안 제품은 멈춘다. 그리고 다시 쓴 앱이 원래 앱과 같은지 확인할 방법이 한 번의 거대한 QA뿐이다. 화면 단위로 옮기면 화면 단위로 확인하고, 화면 단위로 내보낼 수 있다.

## 규칙 3. 끝에서부터, 그리고 옮기면 바로 지운다

순서는 리프에서 루트로 잡았다. 다른 화면으로 이어지지 않는 맨 끝 화면부터 옮긴다. 설정의 하위 화면이나 내역 화면 같은 것들이다.

끝 화면은 의존하는 게 적다. 옮겨도 다른 화면이 영향을 받지 않는다. React Native 쪽에서는 버튼을 눌렀을 때 자기 화면을 여는 대신 브리지를 통해 네이티브 Activity를 열기만 하면 된다.

그리고 화면을 옮기면 React Native 쪽 화면을 바로 지웠다. "혹시 모르니 남겨두자"는 하지 않았다. 남겨두면 같은 화면이 두 개가 되고, 한쪽만 고치는 일이 생긴다.

## 규칙 4. 쪼갤 수 없는 것은 마지막에 한 묶음으로

끝에서부터 올라오다 보면 쪼갤 수 없는 덩어리를 만난다. 탭이 달린 메인 화면이다.

탭 화면은 push로 쌓이는 화면이 아니다. 한 화면 안에서 내용만 갈아 끼운다. 그래서 탭 하나만 네이티브로 옮길 수가 없다. 하단 바를 네이티브로 바꾸는 순간 모든 탭이 따라와야 한다.

처음 계획에서는 탭들을 따로따로 일정에 넣었다. 중간에 고쳤다. 탭 전부와 그걸 담는 화면을 한 묶음으로 합쳐서 맨 뒤로 보냈다.

대신 묶음 안에서 미리 할 수 있는 건 미리 했다. 데이터 계층을 먼저 만들고, 화면을 먼저 만들어 프리뷰로 확인해두면, 마지막에 갈아 끼우는 일만 남는다.

## 규칙 5. 큰 화면은 단계로 나눈다

채팅 화면은 한 번에 옮기기에 너무 컸다. Kotlin 4,912줄에 XML 2,901줄이었다. 세 단계로 나눴다.

1. React Native 껍데기에서 빼내 Activity로 만든다. 화면 구현은 그대로 둔다.
2. 메시지 목록만 Compose로 바꾼다.
3. 나머지 껍데기까지 Compose로 바꾼다.

단계마다 따로 배포할 수 있게 한 것이 핵심이다. 1단계만 끝나도 React Native에서는 벗어난다. 뒤 단계에서 문제가 생기면 그 단계만 되돌린다.

## 규칙 6. 옮길 때는 똑같이 옮긴다

옮긴 화면은 기기에 띄워서 원래 화면과 나란히 놓고 봤다. 간격, 글자 굵기, 색, 모서리. 코드 리뷰를 통과한 화면이 눈으로 보면 달랐다.

기준은 원래 화면이다. 더 낫게 고치고 싶은 곳이 보여도 고치지 않는다. 옮기는 일과 고치는 일을 섞으면, 나중에 뭔가 달라졌을 때 마이그레이션 때문인지 개선 때문인지 알 수 없다. QA도 "원래와 같은가" 하나만 보면 된다.

같은 부품을 여러 번 만들지 않는 것도 여기에 들어간다. 화면을 하나씩 옮기다 보면 댓글 아이템이나 상단 바가 화면마다 조금씩 다르게 생긴다. 공용 컴포넌트를 만들어두고, 옮길 때마다 이미 있는지 먼저 찾았다.

## 규칙 7. 화면이 몰래 하던 일을 찾는다

마지막에 가장 조심한 부분이다. React Native의 메인 화면은 화면만 그리고 있던 게 아니었다.

- 앱이 닫힐 때 리스너를 해제하고 재생 중인 것을 멈추는 정리 작업
- 다른 화면에서 돌아올 때 특정 탭으로 옮겨주는 일. 네이티브가 JS로 이벤트를 보내고 JS가 탭을 바꿨다.
- 조건에 따라 띄우는 안내 팝업

이런 건 화면 목록에 없다. 화면을 다 옮겼다고 메인을 지우면 조용히 사라진다. 크래시가 나지 않으니 한참 뒤에 "이거 원래 됐는데"로 돌아온다.

지우기 전에 메인 화면의 코드를 처음부터 끝까지 읽고, 화면을 그리는 것 말고 하는 일을 전부 적었다. 그걸 하나씩 네이티브로 옮긴 다음에 지웠다.

## 지우는 날

지우는 건 하루였다. 바깥에서 안쪽 순서로 커밋을 나눴다.

1. 번역 문구 원본을 한곳으로 합친다. React Native와 안드로이드가 따로 들고 빌드 때 복사하고 있었다.
2. 네이티브가 쓰지만 이름은 React Native 번들 규칙을 따르던 리소스의 이름을 바꾼다.
3. 안드로이드 코드에서 React Native 메인, 브리지 모듈, 뷰 매니저를 지운다.
4. Gradle에서 React Native 플러그인과 자동 링크, node_modules 참조를 지운다.
5. JS 소스와 도구 설정, 번들 리소스를 지운다. CI에서 yarn 설치와 JS 번들 단계도 뺀다.

마지막 커밋 하나가 파일 407개, 26,429줄 삭제였다. 다섯 커밋을 합치면 3만 줄이 넘는다.

순서를 지킨 이유는 단계마다 빌드를 확인하기 위해서다. 그리고 화면을 옮기는 PR과 지우는 PR을 따로 올렸다. 지우는 쪽에서 문제가 나면 그것만 되돌린다.

## 걷어내고 나서 풀리는 것들

React Native가 있어서 미뤄둔 일들이 있다.

DI를 바꾸는 일이 그랬다. React Native 브리지 모듈은 React Native가 직접 만들기 때문에 DI 프레임워크를 바꾸려면 우회로가 필요했다. 이제 그 걸림돌이 없다.

화면 사이의 이동도 그렇다. 지금은 화면마다 Activity인데, 그렇게 한 이유의 절반은 React Native에서 열기 쉬워서였다.

빌드 시간은 쟀다. 앱 두 종을 차례로 빌드하는 스테이징 빌드에서, Gradle 빌드 단계의 합계가 9분 23초에서 3분 47초가 됐다. 60% 줄었다. 의존성이 바뀐 직후의 첫 빌드는 캐시를 못 써서 오히려 10분 9초가 걸렸고, 두 번째 빌드부터 이 숫자가 나왔다.

앱 용량도 줄었다. 스테이징 APK 기준으로 235MB였던 앱이 137MB가 됐다. 42% 줄어서 거의 반이다. React Native 런타임과 JS 번들, 그리고 React Native 라이브러리들이 들고 있던 네이티브 라이브러리가 한꺼번에 빠진 결과다.

PR 검증도 잡 전체로 보면 9분 12초에서 7분 6초로 줄었다. Node 설치와 `yarn install` 단계가 통째로 빠진 몫이 크다. 컴파일 단계만 보면 거의 그대로인데, PR 검증은 원래부터 JS 번들을 만들지 않았기 때문이다.

## 돌아보면

1년 반 동안 한 일을 한 줄로 줄이면 이렇다. 새로 쌓이는 걸 막고, 끝에서부터 옮기고, 옮기면 지우고, 쪼갤 수 없는 것만 마지막에 한 번에 했다.

가장 오래 걸린 건 코드를 쓰는 일이 아니었다. 원래 화면이 무엇을 하고 있는지 알아내는 일이었다. 그리는 것은 보면 안다. 그리지 않는 것은 읽어야 안다.
