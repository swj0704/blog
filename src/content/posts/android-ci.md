9월 말까지 블루밍톡 안드로이드에는 CI가 사실상 없었다. PR이 올라와도 컴파일이 되는지 확인하는 단계가 없었고, 릴리스는 내 컴퓨터에서 손으로 빌드했다.

그래서 붙이기로 했다. 결과부터 말하면 PR 검증은 5~7분, 스테이징 빌드는 7분 40초가 됐다. 거기까지 가는 길은 이랬다.

## 첫 시도는 45분 뒤에 죽었다

처음 만든 PR 게이트는 45분 타임아웃에 걸려 실패했다. 캐시가 없는 상태에서는 Gradle 설정 단계만 15분이 걸렸다.

두 번째 시도는 1분 만에 실패했다. 러너 디스크를 확보하려고 넣은 정리 단계가 yarn 경로까지 지워버렸다. 빨리 실패한 건 발전이라고 해야 할지 모르겠다.

## assemble을 할 이유가 없었다

돌아가게 만든 뒤에 보니 PR 하나 검증하는 데 캐시가 없으면 38~44분, 있어도 20~24분이 걸렸다. 그런데 PR 게이트가 확인하려는 건 "이 코드가 컴파일되는가"다. APK까지 만들 필요가 없다.

assemble을 컴파일 태스크로 바꿨다. 실행되는 태스크가 791개에서 548개로 줄었고, 첫 실행 11분, 캐시가 맞으면 5~7분이 됐다.

## 54분짜리 스테이징 빌드

스테이징 APK를 만드는 빌드는 GitHub 기본 러너(2코어, 7GB)에서 54분이 걸렸다. 나온 APK는 321MB였다.

먼저 ABI를 4개에서 2개(arm64-v8a, armeabi-v7a)로 줄였다. 그래도 러너 자체가 느렸다. 같은 빌드가 개발용 맥에서는 몇 분이면 끝난다. 그러면 거기서 돌리면 된다.

self-hosted 러너를 붙였다. 신경 쓴 건 두 가지다.

- 러너를 특정 컴퓨터가 아니라 라벨에 묶었다. 지금은 내 컴퓨터지만, 다음 사람 컴퓨터로 바꿀 때 워크플로를 고칠 필요가 없다.
- 러너 전용 Gradle 홈을 따로 뒀다. 내 개발 설정이 CI 빌드에 섞이지 않는다.

첫 실행은 전용 홈이 비어 있어서 Gradle만 19분 40초가 걸렸다. 그다음부터는 잡 전체가 7분 40초다.

## 0MB를 저장하는 데 4분 13초

self-hosted로 옮기고 나서 잡 맨 끝이 이상하게 길었다. 로그를 보니 yarn 캐시를 저장하는 단계가 "0 MB"를 찍은 채 4분 13초 동안 멈춰 있었다.

self-hosted 러너는 디스크가 그대로 남아 있어서 캐시를 올리고 내릴 이유가 없다. 캐시 저장을 껐다.

## 남은 시간은 어디서 쓰이나

스테이징 빌드의 태스크는 1,078개다. 그중 우리 코드가 약 150개이고, 약 920개는 React Native 라이브러리 모듈이다. 앱에 아직 React Native가 남아 있어서다.

빌드 시간을 더 줄이려면 Gradle 옵션을 만질 게 아니라 React Native를 걷어내야 한다. 그건 지금 하고 있는 Compose 마이그레이션의 끝에 있다.

## 빌드를 사람에게 전달하기

빌드가 자동으로 돌아도 테스터 손에 APK가 가야 한다. 테스트 폰 중에는 구글 서비스가 없는 기기가 있어서 Firebase App Distribution을 쓸 수 없었다. 대신 빌드가 끝나면 봇이 APK를 슬랙 채널에 올린다. 파일명에는 버전과 빌드 시각을 넣었다.

릴리스도 자동으로 바꿨다. `release/X.Y.Z` 브랜치를 master에 머지하면 빌드가 돈다. versionName은 브랜치 이름에서 가져오고, versionCode는 직전 릴리스 태그에 적힌 값에 1을 더한다. 버전을 적어두던 파일은 지웠다. 태그가 장부다.

## 정리

| | 전 | 후 |
|---|---|---|
| PR 검증 | 없음 → 첫 시도 45분 타임아웃 | 5~7분 |
| 스테이징 빌드 | 54분 | 7분 40초 |
| 릴리스 | 로컬 수동 빌드 | master 머지 시 자동 |

가장 효과가 컸던 건 기술이 아니라 질문이었다. "이 단계가 확인하려는 게 뭔가"를 물으니 assemble이 빠졌고, "이걸 왜 느린 컴퓨터에서 돌리나"를 물으니 러너가 바뀌었다.
